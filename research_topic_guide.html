Step-by-step research guide for Behaviour-Adaptive Anomaly Detection in OS Telemetry

Recommended research topic — final year B.Tech (CS)
Behaviour-Adaptive Anomaly Detection in Personal OS Telemetry Using Personalized User Baselines
Why this is the right pick: it is the biggest innovation in your project, has a clear measurable gap in existing literature, is directly tied to your code, and produces quantifiable results for a paper.

The research gap in one sentence: Every existing AIOps anomaly detection system uses generic, population-wide thresholds — none builds a personal behavioural baseline per individual user's OS usage pattern to reduce false positives.

Phase B — define your contribution   Steps 4–5
4
Write your research gap and contribution statement
Week 3

Before touching your implementation further, write exactly three things on paper. This is the most important step — it defines the entire paper and keeps your implementation focused. Every design decision in your code should trace back to this statement.

Write these three things (draft, 1 paragraph each)
The problem: "Existing OS monitoring tools apply generic, population-wide thresholds for anomaly detection, ignoring the fact that different users have fundamentally different usage patterns. A developer's 85% CPU during compilation is normal; the same value from an idle user indicates a problem."
The gap: "No existing work builds a behaviour-adaptive, per-user baseline for OS performance telemetry that distinguishes personal usage patterns (GAMING, CODING, BROWSING, IDLE) and uses them as dynamic anomaly thresholds."
Your contribution: "We propose a Behaviour Learning Engine that clusters OS telemetry by time-of-day and activity pattern to build a personal baseline per device, reducing false positives by X% compared to generic threshold approaches."

Phase C — build & measure   Steps 6–7
6
Design your experiment with two conditions to compare
Month 2–3

A research paper needs a comparison, not just a demo. You must run the same anomaly detection with (A) a generic threshold and (B) your personal behaviour baseline, then measure which produces fewer false positives and more true detections. This is your Table 1 or Figure 4 in the paper.

Experimental design
Condition A (baseline): Generic threshold — CPU > 80% = anomaly, RAM > 85% = anomaly, regardless of user or time
Condition B (your system): Personal behaviour baseline — flag only when deviation > 2 standard deviations from the user's hourly mean for that activity pattern
Collect data on 3–5 machines for at least 7 days each — one machine per distinct usage profile (developer, student, gamer, office user)
Inject synthetic anomalies at known times (e.g. run a CPU stress test) so you have ground truth for precision/recall calculation
Metrics to report in the paper
Precision
TP / (TP + FP)
Recall
TP / (TP + FN)
F1 Score
harmonic mean of P and R
False positive rate
FP / (FP + TN)
Expected result: your personal baseline should reduce false positives by 30–60% compared to generic thresholds for mixed-use machines

Phase D — write the paper   Step 8
8
Write the paper in this exact section order
Month 4–5

Counter-intuitively, do not write your paper from Section 1 to the end. Write in this order — each section builds on the one before, and your experiments give you the numbers that make the abstract and introduction credible.

Writing order (not the reading order)
1st — Methodology (Section 4): Describe your Behaviour Learning Engine, ensemble model, and personal baseline algorithm. Write it while the code is fresh.
2nd — Experiments (Section 5): Run your A vs B comparison, collect numbers, build your tables and figures. These are the core of the paper.
3rd — Related Work (Section 2): Now that you know what you did, map it against the literature you collected in Steps 1–3. Be specific: "Unlike [Liu et al., 2008], our approach adapts the contamination parameter per user."
4th — Introduction (Section 1): Write this last among the body sections. Use your experimental numbers here: "Our system reduced false positives by 47% compared to generic threshold detection."
5th — Abstract (150 words max): Written last. One sentence each: problem, gap, method, key result, claim.
